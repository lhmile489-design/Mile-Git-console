# Mile Git Management · 体验升级计划

> 版本：v1 草案 · 2026-10-28
> 基线：`refactor/soft-ui` 分支，应用版本 2.0.0
> 依据：对渲染进程、主进程、preload 和 store 的代码审查，结论来自实际读到的代码和 grep 结果，不是对竞品的印象。
> 状态：待确认。确认优先级后按阶段实施，每个阶段单独提交。

---

## 1. 现状摘要

已经具备：仓库导入与搜索、工作区暂存与提交、分支切换与新建、获取/拉取/推送、提交历史与只读 diff、浅色深色主题、三个破坏性操作的二次确认。

体验上的主要缺口，按用户感知从强到弱排列：

| 序号 | 缺口 | 依据 |
|---|---|---|
| 1 | 状态只在手动操作后刷新。在外部编辑器改了文件，回到应用看到的还是旧列表 | 没有找到窗口聚焦刷新，也没有文件监听 |
| 2 | 获取/拉取/推送只有转圈，没有进度，也不能取消 | `git:progress` 在 preload 白名单里，但主进程没有任何发送端 |
| 3 | 冲突只有一条 3 秒后消失的提示。没有冲突文件的专门入口，没有「中止合并」 | `pull` 只设置 notice 文案；合并冲突在状态里只是一个标签 |
| 4 | 分支能力不完整：合并和删除分支的 IPC 已经有了，界面没有入口；只显示本地分支，看不到远端分支 | 组件里没有用到 `mergeBranch`、`deleteBranch`；`BranchSelector` 只取 `!isRemote` |
| 5 | 缺少常用 Git 操作：stash、amend、tag、克隆、撤销丢弃 | preload 的 channel 列表里没有这些；丢弃未跟踪文件直接 `rmSync`，不可恢复 |
| 6 | 键盘支持只到「Esc 关菜单」和「Ctrl+Enter 提交」，没有全局快捷键和命令面板 | 全部 `onKeyDown` 只出现在 ActionBar、BranchSelector、CommitPanel、ResizeHandle |
| 7 | Diff 只有逐行视图，没有并排、字级高亮，也不能按块或按行暂存 | `DiffViewer` 只渲染行；根文档规划了「部分暂存」但未实现 |
| 8 | 历史没有搜索和过滤，只有「加载更多」按钮，图谱是单线 | 只有仓库搜索，没有提交搜索；`limit: 50` |
| 9 | 窗口大小位置不记忆，提交草稿不保存 | 没有找到相关持久化代码 |
| 10 | 仓库目录被移动或删除后，只会得到原始 git 报错 | 路径存在性只在导入时检查一次 |
| 11 | 关闭按钮实际是隐藏到托盘，但界面里没有任何提示 | 主进程拦截 `close`；渲染层没有出现「托盘」字样 |
| 12 | 设置页只有主题。`defaultRemote`、提交模板、语言在设置存储里有默认值，但没有界面 | `SettingsPage` 只有主题和关于 |
| 13 | 无障碍：只有提示卡片是 `role="status"`，状态刷新、加载没有 live region | grep 只命中 `App.tsx` 一处 |

## 2. 阶段划分

建议顺序：E，A，B，C，D。E 先做是因为其中有会丢数据或影响退出的问题，后面的功能都建立在它之上。

### 阶段 E：质量与安全前置

对应上一轮代码审查里的 Important 项，已有单独任务卡片，不在本计划里重复展开。这里只列体验升级需要依赖的部分。

| 项 | 内容 | 规模 |
|---|---|---|
| E1 | 退出行为：`close` 拦截要区分「用户点关闭」和「应用退出」，否则系统关机、macOS Cmd+Q 会被拦住 | S |
| E2 | 单实例锁：避免第二个进程同时写同一个 SQLite | S |
| E3 | git 参数防注入，`repoPath` 必须是已登记仓库 | M |
| E4 | 错误信息脱敏，避免远端地址里的凭据进入日志表 | S |
| E5 | 给 `parseDiff`、`parseCommitLog`、`parseNumstat` 补单元测试；把这次的 Playwright 验证脚本沉淀成仓库内的冒烟脚本 | M |

### 阶段 A：日常手感（高感知，低风险）

| 项 | 内容 | 涉及层 | 规模 |
|---|---|---|---|
| A1 | 自动刷新：窗口获得焦点时刷新状态；之后再评估对工作区做 `fs.watch`（带防抖） | 渲染 + 主进程 | S 到 M |
| A2 | 长操作进度：接上 `git:progress`，按钮上显示阶段文字；超过设定时间给出「取消」 | 主进程 + preload + 渲染 | M |
| A3 | 快捷键：F5 刷新、Ctrl+1 与 Ctrl+2 切换更改和历史、Ctrl+Shift+P 推送、Ctrl+Shift+L 拉取；菜单项上显示快捷键提示 | 渲染 | S |
| A4 | 命令面板（Ctrl+K）：切换仓库、切换分支、执行获取/拉取/推送、打开设置 | 渲染 | M |
| A5 | 记忆窗口大小、位置和最大化状态 | 主进程 | S |
| A6 | 提交草稿按仓库保存，切换仓库不串内容；提交成功才清空 | 渲染 | S |
| A7 | 仓库失效处理：列表项标注「路径不存在」，提供「重新定位」与「移除」 | 渲染 + 主进程 | S |
| A8 | 拖拽文件夹到窗口导入；窗口关闭时首次提示「已最小化到托盘」，可在设置里关闭提示 | 渲染 + 主进程 | S |
| A9 | 提示卡片支持操作按钮（如「查看详情」「撤销」），同时出现多条时叠放而不是互相覆盖 | 渲染 | S |

### 阶段 B：补全核心 Git 工作流

这一阶段新增 IPC，需要同步更新 `docs/IPC契约.md`。

| 项 | 内容 | 新增 IPC | 规模 |
|---|---|---|---|
| B1 | 分支菜单加入远端分支、合并、删除。合并和删除接现有 IPC，删除走 `ConfirmDialog`，强制删除单独确认 | 无 | M |
| B2 | 冲突处理：冲突文件单独分组并置顶；顶部横幅显示「正在合并，N 个冲突」；提供「中止合并」「在外部编辑器打开」「标记为已解决」 | `git:merge:abort` 等 | L |
| B3 | Stash：保存（可带说明）、列表、应用、弹出、删除 | `git:stash:*` | M |
| B4 | 修改上一次提交（amend）。已经推送过的提交要在确认框里明确提示后果 | `git:commit:amend` | M |
| B5 | 丢弃可撤销：丢弃前把内容备份到用户数据目录，10 分钟内可在提示卡片上点「撤销」恢复 | `git:discard:restore` | M |
| B6 | 历史中标出 ahead、behind 提交和远端分支标签；推送前显示将要推送的提交列表 | 无或 `git:log:range` | M |
| B7 | 克隆仓库：输入地址和目录，显示进度，完成后自动导入。需要先确定凭据方案，不把凭据写进库 | `repo:clone` | L |
| B8 | 标签：创建、推送、删除 | `git:tag:*` | M |

## 3. 需要你决定的事

1. 目标使用场景是「个人管理多个本地仓库」，还是要接近 GitHub Desktop 的完整功能？这决定阶段 C 的 C3、C7 做不做。
2. 克隆（B7）涉及凭据。是依赖系统已有的 git 凭据管理器，还是应用内提供登录？前者简单，后者要做安全存储。
3. 是否需要 Pull Request、Issue 这类托管平台功能？目前应用与平台无关，加入后需要账号体系，建议单独立项。
4. 阶段 E 的任务卡片已经建好，但对应 session 因仓库未信任没有启动。需要你先在那个 session 里点信任，或者回到本 session 来做。

## 4. 本次审查没有确认的内容

- 提交草稿是否会在切换仓库时串到另一个仓库：`CommitPanel` 的输入状态是组件内部 `useState`，切换仓库时组件没有重新挂载的迹象，但我没有实际操作验证。
- `git:progress` 能否从 simple-git 取得有意义的进度：simple-git 有 `progress` 回调，但各命令输出的粒度需要实测。
- `fs.watch` 在 Windows 上对大型仓库的开销，需要在真实大仓库上测，不能只凭文档判断。
- 阶段内各项的规模（S、M、L）是按代码改动范围估的粗略值，没有按实测工时。

## 5. 约束

沿用现有规范：渲染进程不直接用 Node API，颜色一律走 `tokens.css`，新增 IPC 先改契约文档，破坏性操作必须二次确认，每项完成后跑 typecheck、lint、build 并截图，不使用 emoji。
